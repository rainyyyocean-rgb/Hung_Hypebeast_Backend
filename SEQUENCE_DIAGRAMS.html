3.2.1 Luồng tạo đơn hàng với xử lý Race Condition (CRITICAL)

sequenceDiagram participant Customer participant Frontend participant CartAPI participant OrderAPI participant ProductSkuRepo participant OrderRepo participant EmailService Customer->>Frontend: Thêm sản phẩm vào giỏ Frontend->>CartAPI: POST /api/v1/cart/validate CartAPI->>ProductSkuRepo: Check available quantity CartAPI-->>Frontend: Validation result Customer->>Frontend: Điền thông tin & bấm "Đặt hàng" Frontend->>OrderAPI: POST /api/v1/orders Note over OrderAPI: CRITICAL: Pessimistic Lock OrderAPI->>ProductSkuRepo: SELECT ... FOR UPDATE (Lock) alt Đủ hàng OrderAPI->>ProductSkuRepo: Deduct quantity (trừ stock ngay) OrderAPI->>OrderRepo: Create order (PENDING for SePay, CONFIRMED for COD) Note over OrderAPI: Set expired_at = now + 15min (for SePay) OrderAPI->>EmailService: Send confirmation email (COD only) OrderAPI-->>Frontend: Order created (tracking_token) else Không đủ hàng OrderAPI-->>Frontend: 400 Bad Request (Hết hàng) end

📝 Giải thích luồng:

  1. Validate Cart: Check tồn kho trước khi checkout
  2. Create Order với Lock: Pessimistic lock đảm bảo không có race condition
  3. Trừ stock ngay: Khi tạo đơn hàng, stock bị trừ luôn
  4. COD: Status = CONFIRMED, gửi email ngay
  5. SePay: Status = PENDING, set expired_at, chờ thanh toán
  6. Nếu hết thời gian: Scheduler tự động cancel và hoàn stock
🔒 Điểm quan trọng: Sử dụng Pessimistic Lock (SELECT ... FOR UPDATE) để đảm bảo chỉ 1 transaction xử lý tại 1 thời điểm, tránh overselling khi 2 người mua cùng lúc.

3.2.2 Luồng thanh toán SePay

sequenceDiagram participant Customer participant Frontend participant OrderAPI participant ProductSkuRepo participant SePay participant WebhookAPI participant OrderRepo participant EmailService participant Scheduler Customer->>Frontend: Chọn thanh toán SePay Frontend->>OrderAPI: POST /api/v1/orders (paymentMethod=SEPAY) Note over OrderAPI: Pessimistic Lock OrderAPI->>ProductSkuRepo: SELECT ... FOR UPDATE & Deduct quantity OrderAPI->>OrderRepo: Create order (status=PENDING, expired_at=now+15min) OrderAPI-->>Frontend: Order created (tracking_token) Frontend->>Customer: Hiển thị QR code / Payment link alt Thanh toán thành công trong 15 phút Customer->>SePay: Quét QR / Thanh toán SePay->>WebhookAPI: POST /api/v1/payments/sepay-webhook-mock WebhookAPI->>OrderRepo: Update status: PENDING → CONFIRMED WebhookAPI->>OrderRepo: Clear expired_at WebhookAPI-->>SePay: 200 OK WebhookAPI->>EmailService: Send confirmation email else Không thanh toán trong 15 phút Scheduler->>OrderRepo: Scan expired orders (every 1 minute) Note over Scheduler: Find orders: status=PENDING AND expired_at < now Scheduler->>OrderRepo: Update status: PENDING → CANCELED Scheduler->>ProductSkuRepo: Restore stock quantity Scheduler->>EmailService: Send cancellation email (optional) end

📝 Giải thích luồng:

  1. Tạo đơn PENDING: Khi chọn SePay, order có status = PENDING, stock đã bị trừ
  2. Webhook xử lý thanh toán: SePay gọi webhook khi khách thanh toán thành công
  3. Auto-cancel: Scheduler tự động hủy đơn sau 15 phút nếu không thanh toán và hoàn lại stock
⏰ Cơ chế giữ hàng: Stock bị trừ ngay khi tạo đơn. Nếu không thanh toán trong 15 phút, scheduler tự động cancel đơn và hoàn lại stock. Không cần bảng reservation riêng!

3.2.3 Luồng xử lý Race Condition (2 người mua cùng lúc)

sequenceDiagram participant User1 participant User2 participant OrderService participant ProductSkuRepo participant OrderRepo Note over ProductSkuRepo: SKU có quantity = 1 (last item) par User 1 và User 2 bấm Đặt hàng cùng lúc User1->>OrderService: createOrder(sku_id=1, qty=1) User2->>OrderService: createOrder(sku_id=1, qty=1) end Note over OrderService: Request User 1 được xử lý trước OrderService->>ProductSkuRepo: findByIdWithLock(sku_id=1) Note over ProductSkuRepo: SELECT FOR UPDATE - Lock acquired by User1 ProductSkuRepo->>OrderService: ProductSku (quantity=1, LOCKED) Note over OrderService: Validate: 1 >= 1 ✅ OrderService->>ProductSkuRepo: Deduct quantity (1 - 1 = 0) OrderService->>OrderRepo: Create order (status=PENDING/CONFIRMED) OrderRepo->>OrderService: Order created OrderService->>User1: ✅ Đặt hàng thành công! Note over ProductSkuRepo: Lock released Note over OrderService: Giờ xử lý request User 2 OrderService->>ProductSkuRepo: findByIdWithLock(sku_id=1) Note over ProductSkuRepo: SELECT FOR UPDATE - Lock acquired by User2 ProductSkuRepo->>OrderService: ProductSku (quantity=0, LOCKED) Note over OrderService: Validate: 0 >= 1 ❌ OrderService->>User2: ❌ Hết hàng (InsufficientStockException)

📝 Giải thích luồng:

  1. Parallel Requests: 2 user bấm đặt hàng cùng lúc
  2. Pessimistic Lock (User 1):
    • OrderService gọi findByIdWithLock() → SELECT FOR UPDATE
    • Database lock row của SKU, User 2 phải chờ
    • Validate: 1 >= 1 ✅ → Trừ stock → Tạo order thành công
    • Lock được release
  3. Pessimistic Lock (User 2):
    • Giờ User 2 mới được xử lý
    • Lấy được lock (User 1 đã release)
    • Validate: 0 >= 1 ❌ → Throw InsufficientStockException
  4. Kết quả: User 1 mua được, User 2 nhận thông báo hết hàng (KHÔNG bị overselling)
🎯 Vấn đề được giải quyết: Đây là vấn đề CRITICAL mà khách hàng nhấn mạnh trong email: "Đợt trước sale, cái áo còn đúng 1 cái size L. Hai ông khách cùng bấm mua một lúc... cuối cùng anh phải gọi điện xin lỗi 1 ông, bị chửi te tua." Giờ với Pessimistic Lock, vấn đề này không còn nữa!

🔒 Cơ chế Pessimistic Lock:
  • SELECT FOR UPDATE: Lock row trong database, transaction khác phải chờ
  • Atomic Operation: Check và update quantity trong 1 transaction
  • No Race Condition: Không thể có 2 transaction cùng đọc quantity=1
  • FIFO Processing: Request đến trước được xử lý trước
